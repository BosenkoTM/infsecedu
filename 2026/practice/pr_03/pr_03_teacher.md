# Практическая работа № 3 — материалы преподавателя
## Расследование инцидента в цифровой образовательной среде

**Максимальная оценка:** 15 баллов  
**Студенческий файл:** `pr_03.md`  
**Результат студента:** один файл `pr_03_Фамилия.md`

---

# 1. Методика проведения

Практика упрощена до одной встроенной подборки журналов.

Студент должен показать не навыки цифровой криминалистики, а базовую способность:

> **сопоставить события → выделить подтверждённые факты → сформулировать рабочую гипотезу → определить масштаб → локализовать → восстановить → сообщить без обвинений**

Не требовать:

- расчёта SHA-256;
- отдельных исходных файлов;
- отдельной карточки инцидента;
- 10 отдельных документов;
- полного форензик-исследования устройства.

Критически важно, чтобы студент не выдавал предположение о фишинге за установленный факт.

---

# 2. Ориентир общего решения

## 2.1. Аномальная последовательность

Основная последовательность:

1. `M02` — доставлено письмо с просьбой подтвердить учётную запись;
2. `M03` — зафиксирован переход по URL;
3. `A02` — неудачный вход с `203.0.113.77`;
4. `A03` — успешный вход с того же IP;
5. `A04` — создана сессия;
6. `L02` — экспортировано 31 участник курса;
7. `L03`, `L04` — изменены две оценки;
8. `L05` — создан API-токен;
9. `L06` — скачано 12 файлов задания;
10. `A06`, `L07–L09` — обычный локальный пользователь снова появляется в системе и просматривает курс/оценки.

Именно совокупность этих событий делает компрометацию рабочей гипотезой.

---

## 2.2. Подтверждённые факты

Примеры:

- `M03`: пользователь перешёл по URL из письма в 08:44:03;
- `A03`: в 08:47:41 выполнен успешный вход с `203.0.113.77`;
- `L02`: в 08:51:12 экспортированы 31 запись;
- `L03`: изменена оценка `student-S014` с 4 на 5;
- `L04`: изменена оценка `student-S022` с 3 на 5;
- `L05`: создан токен `T91`;
- `L06`: скачано 12 файлов.

Не является фактом:

- что пользователь ввёл пароль на фишинговой странице;
- что IP принадлежит злоумышленнику;
- что скачанные/экспортированные данные были переданы третьим лицам;
- что именно преподаватель совершал подозрительные действия.

---

## 2.3. Рабочая гипотеза

Допустимая формулировка:

> После перехода по ссылке из сообщения M03 учётная запись `teacher.ivanova` могла быть скомпрометирована. Через несколько минут с внешнего IP `203.0.113.77` выполнен успешный вход, после которого произошли необычные действия: экспорт участников, изменение двух оценок, создание API-токена и скачивание работ. Прямая причинная связь между письмом и компрометацией по имеющимся журналам не доказана и требует дополнительных данных.

---

## 2.4. Дополнительные проверки

Хорошие ответы:

- журнал MFA;
- user-agent входов;
- журнал прокси/браузера;
- DNS;
- журнал создания и использования токенов;
- список всех активных сессий;
- подтверждение преподавателя;
- журнал изменения оценок до/после;
- журнал выгрузок;
- журнал почтовой системы с URL reputation.

---

## 2.5. Масштаб

Ориентир:

| Параметр | Ответ |
|---|---|
| Подозрительная учётная запись | `teacher.ivanova` |
| Начало подтверждённой подозрительной активности | 08:47:26 (`A02`) либо 08:47:41 (`A03`) |
| Связанное более раннее событие | 08:44:03 (`M03`) |
| Последнее подозрительное действие с внешнего IP | 09:03:18 (`L06`) |
| Внешний IP | `203.0.113.77` |
| Курс | `course-INF-7A` |
| Экспорт | 31 участник (`L02`) |
| Изменения | `student-S014`, `student-S022` |
| Новый доступ | API-токен `T91` |

Допустимо различать:
- **подтверждённый подозрительный интервал**: 08:47–09:03;
- **возможный период компрометации**: начинается раньше, если M03 связан с причиной.

---

## 2.6. Локализация

Хороший порядок:

1. сохранить/зафиксировать журналы;
2. отозвать токен `T91`;
3. завершить подозрительные активные сессии;
4. временно заблокировать или ограничить аккаунт `teacher.ivanova`;
5. проверить и временно защитить изменённые данные/экспорт;
6. инициировать смену учётных данных и проверку MFA.

Допустим другой порядок при хорошем обосновании.

Полное отключение LMS по этому кейсу обычно избыточно.

---

## 2.7. Восстановление

Минимальные условия:

1. пароль изменён через доверенный канал;
2. MFA проверена/перенастроена;
3. все подозрительные сессии завершены;
4. токен `T91` отозван, проверено отсутствие других неизвестных токенов;
5. оценки `S014` и `S022` проверены по доверенному источнику и при необходимости восстановлены;
6. журналы снова поступают;
7. нет новых подозрительных входов.

# 4. Ориентиры решений 25 вариантов

## Вариант 1. Фишинговое письмо

1. Признаки: внешний похожий адрес `edu-help.example`, требование «подтвердить учётную запись», последующий URL click. Сам по себе домен в учебном кейсе не доказывает вредоносность.
2. Можно утверждать только временную близость M03 и A03. Причинность — гипотеза.
3. Правило: не вводить пароль по ссылке из неожиданного письма; открыть сервис через известный адрес и сообщить о подозрении.

## Вариант 2. Успешный вход

1. A02 — failed, A03 — success, A04 — session created.
2. Новый IP может быть легитимным: мобильный интернет, VPN, командировка.
3. Усиливают подозрение: M03 перед входом, необычные действия L02–L06, параллельный привычный локальный IP позже.

## Вариант 3. Экспорт участников

1. L02 — экспорт 31 строки.
2. Главный риск — конфиденциальность.
3. Меры обнаружения: журналировать массовые выгрузки; оповещать о необычном экспорте/новом IP.

## Вариант 4. Изменение оценок

1. L03: S014 4→5; L04: S022 3→5.
2. Проверить исходные оценки по доверенному журналу/ведомости и последующие изменения.
3. Восстановить по контрольной ведомости или подтверждённому источнику и зафиксировать корректировку.

## Вариант 5. API-токен

1. L05 создаёт дополнительный механизм доступа.
2. Пароль не инвалидирует автоматически уже созданный токен.
3. Отозвать T91, проверить список токенов, журнал создания/использования, сохранить события.

## Вариант 6. Скачивание работ

1. L06 — скачано 12 файлов.
2. Возможны учебные работы и связанные с ними данные.
3. Проверить перечень файлов и дальнейшие запросы/сетевые события, связанные с сессией.

## Вариант 7. Локальный вход преподавателя

1. A06 и L07–L09 показывают возвращение привычной активности с `10.20.5.14`.
2. Это может означать, что пользователь сам обнаружил изменения, но не доказывает этого.
3. Вопросы: «Входили ли вы около 08:47 с другого подключения?», «Создавали ли токен?», «Меняли ли оценки S014/S022?»

## Вариант 8. Временная линия

1. Ключевые: M03, A03, A04, L02, L03/L04, L05/L06.
2. Подтверждённый интервал подозрительных действий — примерно 08:47:26–09:03:18.
3. Возможная компрометация может начаться раньше; связь с M03 требует проверки.

## Вариант 9. Факты и гипотезы

Факты: M03, A03, L05.  
Гипотезы: фишинг привёл к захвату; внешний IP использовал похищенную сессию.  
Проверки: MFA/user-agent/прокси/опрос пользователя.

## Вариант 10. Масштаб инцидента

1. `course-INF-7A`, S014, S022, token-T91, task-2026-08-20.
2. Просмотр/экспорт: L02, L06; изменение: L03/L04; новый доступ: L05.
3. Первым обычно проверить токен и изменённые оценки: токен продолжает доступ, оценки влияют на целостность.

## Вариант 11. Локализация

1. Отзыв токена, завершение сессий, временная блокировка/смена данных.
2. Сначала сохранить доказательства, затем закрыть механизмы доступа.
3. Компрометация локализована одной учётной записью; отключение всей LMS нарушит обучение без доказанной необходимости.

## Вариант 12. Восстановление аккаунта

1. Новый пароль; MFA; revoke sessions; revoke tokens; проверка оценок; мониторинг.
2. Повторный вход предотвращают пароль/MFA/sessions/tokens.
3. Доверие к данным восстанавливают проверка оценок и журналов.

## Вариант 13. MFA

1. Нужны: был ли challenge, метод, результат, устройство.
2. MFA затруднила бы вход с одним похищенным паролем.
3. Резервный процесс: подтверждённая идентификация + резервный код/аппаратный ключ/служба поддержки.

## Вариант 14. Активные сессии

1. Уже активная сессия может продолжить работу после смены пароля.
2. Отозвать внешнюю и все неизвестные сессии; при сомнении — все сессии аккаунта.
3. Повторный вход только после смены пароля, проверки MFA и закрытия неизвестных токенов.

## Вариант 15. Журналы

1. MFA logs, proxy/DNS, token usage, endpoint/browser.
2. Каждый отвечает на отдельный вопрос: как подтверждён вход, куда обращались, использовался ли токен, что делал endpoint.
3. Отсутствие записи может означать отсутствие логирования, сбой или другой источник.

## Вариант 16. Коммуникация ИТ-службе

Полный ответ должен содержать факты: внешний вход, экспорт, изменения, токен; отдельно гипотезу; запросы: revoke token/sessions, сохранить логи, ограничить аккаунт.

## Вариант 17. Коммуникация педагогам

Ожидается краткое правило: не открывать подозрительные ссылки, не вводить пароль, сообщать о необычном входе/изменениях, не пытаться самостоятельно «исправлять следы».

## Вариант 18. Руководитель

Должны быть: подтверждённый подозрительный вход, затронутый курс, две оценки, экспорт и токен; влияние на учебные данные; указание, что причина пока расследуется.

## Вариант 19. Предупреждение повторения

Техническая: MFA/alerts.  
Организационная: процедура сообщения и отзыва токенов.  
Образовательная: обучение фишингу.  
Приоритет можно дать MFA или мониторингу — при обосновании.

## Вариант 20. Работа без обвинения

1. Возможные системные причины: отсутствие обязательной MFA, слабая культура сообщения, отсутствие alert на новый IP/экспорт.
2. Обвинение заставляет скрывать ошибки и ухудшает время обнаружения.
3. Правило: раннее сообщение приветствуется и рассматривается как часть процесса безопасности.

## Вариант 21. Изменённые оценки

1. S014: 4→5, S022: 3→5.
2. Нужен доверенный источник: журнал до события, ведомость, подтверждение педагога/методиста.
3. Восстановить, зафиксировать изменение, перепроверить аудит.

## Вариант 22. Экспорт данных

1. L02 — 31 строк.
2. Нельзя утверждать, что файл покинул систему/устройство; подтверждён факт экспорта.
3. Проверить download/network/proxy/endpoint и дальнейшие обращения.

## Вариант 23. Токен как механизм закрепления

1. Токен может сохранить доступ независимо от смены пароля.
2. Проверить все токены, время создания, использование, права.
3. Alert на создание токена; ограничение прав/подтверждение чувствительных токенов.

## Вариант 24. Педагогическая непрерывность

1. Например, временная блокировка аккаунта мешает работе.
2. Резерв: временный доступ к материалам через методиста/резервную учётную процедуру без выдачи старого аккаунта.
3. Это сохраняет безопасность и позволяет продолжить занятие.

## Вариант 25. Комплексное расследование

### Задание 1

Хороший набор событий:

- `M03` — переход по ссылке;
- `A03` — успешный внешний вход;
- `L02` — экспорт участников;
- `L03/L04` — изменение оценок;
- `L05` — создание токена.

`L06` также допустимо включить вместо одного из них.

### Задание 2

Ориентир:

> Подтверждено, что после перехода по ссылке M03 произошёл успешный вход с внешнего IP, затем экспорт данных, изменение оценок и создание токена. Рабочая гипотеза — компрометация учётной записи. Не подтверждено, что именно письмо стало причиной и что данные были переданы третьей стороне.

### Задание 3

- локализация: отозвать токен и сессии, временно ограничить аккаунт;
- восстановление: сменить пароль/MFA, проверить и восстановить оценки;
- предупреждение: обязательная MFA + уведомления о новом IP/массовом экспорте или обучение фишингу.

# 5. Коммуникация — ориентир

Пример педагогического сообщения:

> Коллеги, если вы получили неожиданное письмо с просьбой подтвердить учётную запись, не переходите по ссылке и не вводите пароль. Откройте LMS через привычный адрес. Если заметили неизвестный вход, изменение оценок, необычный экспорт или другое действие, которое вы не выполняли, сразу сообщите в ИТ-службу и укажите примерное время события. Не удаляйте письма и не пытайтесь самостоятельно очищать журналы или историю: эти данные могут помочь быстро разобраться в ситуации. Раннее сообщение рассматривается как правильное действие и помогает снизить последствия инцидента.

# 6. Педагогический разбор — ориентир

Хорошая мысль:

> Пользователь должен иметь безопасный и понятный канал сообщения об ошибке без угрозы автоматического наказания. Разбор инцидента сначала направлен на восстановление процесса и устранение системных причин, а не на поиск виновного. Можно использовать короткую форму сообщения и отдельно фиксировать, что раннее уведомление является ожидаемым поведением.
